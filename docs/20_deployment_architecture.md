# Deployment Architecture

Version: V1.0

---

# 1. 目的

本文件定义系统从开发、测试、回测到实盘部署的整体架构、运行方式、进程边界、环境划分、配置管理、监控与恢复机制，确保：

- 回测与实盘部署结构一致
- 策略、风控、执行、数据、报告分层清晰
- 任何单点故障都不会直接导致全局失控
- 实盘系统可观测、可恢复、可审计
- Codex 后续实现时有明确的工程落地边界

部署架构的目标不是复杂，而是稳定、隔离、可恢复。

---

# 2. 部署原则

1. 策略逻辑与执行逻辑必须分离。
2. 回测环境与实盘环境必须隔离。
3. 配置必须外置，禁止硬编码。
4. 所有关键组件必须可独立重启。
5. 所有关键状态必须可持久化恢复。
6. 所有关键操作必须可审计。
7. 实盘系统必须有保护模式。
8. 出现异常时优先保证资金安全。
9. 任何部署变更必须可回滚。
10. 不允许开发环境逻辑直接进入生产而无验证。

---

# 3. 系统分层

建议系统拆分为以下层：

- `data layer`
- `indicator layer`
- `context layer`
- `signal layer`
- `risk layer`
- `execution layer`
- `portfolio layer`
- `backtest layer`
- `reporting layer`
- `monitoring layer`

各层职责必须固定，不得互相越权。

---

# 4. 运行环境划分

系统至少分为三个环境：

## 4.1 Development
开发环境。

用途：

- 本地调试
- 单元测试
- 模块联调
- 小样本回放

特征：

- 不连接真实交易账户
- 可使用模拟数据
- 日志更详细
- 可频繁重启

---

## 4.2 Staging
预发布环境。

用途：

- 回测后验证
- 小规模模拟实盘
- 与真实交易所接口联调
- 验证配置、风控、执行链路

特征：

- 尽量与生产一致
- 可使用测试网或沙盒
- 配置与生产结构一致
- 不允许策略逻辑与生产分叉

---

## 4.3 Production
生产环境。

用途：

- 真实交易
- 真实风控
- 真实执行
- 真实审计

特征：

- 只运行稳定版本
- 只能通过配置切换参数
- 不能随意改代码上线
- 变更必须可回滚

---

# 5. 部署目标

系统部署后至少应支持以下能力：

- 启动全量策略
- 启动单币种策略
- 启动回测任务
- 启动日报任务
- 启动健康检查
- 启动行情同步
- 启动持仓同步
- 启动执行监听
- 启动事件回放
- 启动故障恢复

---

# 6. 推荐运行形态

建议采用“单主进程 + 多模块工作流 + 持久化存储”的结构。

原因：

- 便于调试
- 便于审计
- 便于回放
- 便于逐步重构
- 便于后续容器化或服务化

如果未来需要进一步拆分，也应先保证单进程逻辑清晰，再拆服务。

---

# 7. 推荐目录结构

```text
crypto-mtf-strategy/
├─ docs/
├─ src/
│  ├─ app/
│  ├─ config/
│  ├─ data/
│  ├─ indicators/
│  ├─ context/
│  ├─ signals/
│  ├─ state_machine/
│  ├─ risk/
│  ├─ execution/
│  ├─ portfolio/
│  ├─ backtest/
│  ├─ reporting/
│  └─ utils/
├─ tests/
├─ scripts/
├─ logs/
├─ reports/
├─ data/
├─ configs/
└─ deployments/
````

---

# 8. 进程划分

建议至少划分以下进程或任务单元：

* `market data daemon`
* `strategy engine`
* `execution engine`
* `risk supervisor`
* `portfolio sync daemon`
* `backtest runner`
* `report generator`
* `health monitor`

如果早期不拆进程，也要在代码层保持模块边界。

---

# 9. 数据流架构

建议数据流如下：

```text
market data
  -> data layer
  -> indicator layer
  -> context layer
  -> signal layer
  -> risk layer
  -> execution layer
  -> exchange
  -> position sync
  -> event bus
  -> database
  -> reporting
```

原则：

* 单向流转优先
* 策略判断不应反向污染数据层
* 执行层只反馈结果，不改写决策逻辑

---

# 10. 状态流架构

状态应按以下方向流动：

```text
FLAT
  -> WATCH
  -> PROBE
  -> DIRECT
  -> MANAGE
  -> EXIT
  -> FLAT
```

要求：

* 状态必须持久化
* 状态必须可恢复
* 状态必须有时间戳
* 状态必须有原因字段
* 不允许状态机跨层乱跳

---

# 11. 配置部署

所有配置必须外置。

建议配置分为：

* `strategy.yaml`
* `risk.yaml`
* `execution.yaml`
* `universe.yaml`
* `logging.yaml`
* `backtest.yaml`
* `database.yaml`
* `monitoring.yaml`

配置加载原则：

1. 默认配置先加载
2. 环境配置覆盖
3. 实盘密钥通过环境变量注入
4. 运行时不得修改核心策略配置

---

# 12. 密钥与凭证管理

交易所密钥、数据库密码、告警密钥等必须独立管理。

原则：

* 不写进代码仓库
* 不写进普通配置文件
* 不明文打印到日志
* 不在报表中泄露

建议使用：

* 环境变量
* 密钥文件
* Secret Manager
* 容器挂载密钥

---

# 13. 日志部署

日志必须分层存储：

* `strategy`
* `risk`
* `execution`
* `backtest`
* `audit`
* `system`

日志要求：

* JSON 结构化
* 按天归档
* 支持压缩
* 支持检索
* 支持回放

建议日志目录：

```text
logs/
├─ strategy/
├─ risk/
├─ execution/
├─ backtest/
├─ audit/
└─ system/
```

---

# 14. 数据库存储部署

数据库建议至少承载：

* 行情数据
* 指标结果
* 多周期上下文
* 策略事件
* 信号结果
* 订单与成交
* 持仓快照
* 风控快照
* 回测结果
* 审计日志
* 配置版本

要求：

* 数据库连接要稳定
* 写入操作要幂等
* 关键表必须有索引
* 大表必须考虑归档
* 回测与实盘数据必须可区分

---

# 15. 回测部署

回测部署应与实盘部署共用尽可能多的代码，但不能共用交易副作用。

回测部署要求：

* 使用历史数据源
* 不连接真实下单接口
* 模拟撮合
* 模拟手续费
* 模拟滑点
* 保存回测步骤与结果

回测任务建议独立运行，不与实盘主进程混合。

---

# 16. 实盘部署

实盘部署需要至少包含以下运行单元：

* 行情获取
* 指标计算
* 上下文生成
* 信号生成
* 风控评估
* 执行请求
* 持仓同步
* 事件记录
* 健康监控

实盘部署要求：

* 启动前必须加载最新配置
* 启动后必须同步现有持仓
* 启动后必须检查保护单
* 启动后必须验证交易所连接
* 启动后必须验证数据库可写
* 启动后必须验证风控阈值

---

# 17. 启动流程

建议标准启动流程如下：

1. 加载配置
2. 校验配置版本
3. 连接数据库
4. 加载标的池
5. 拉取最新行情
6. 同步账户与持仓
7. 检查保护单状态
8. 启动事件总线
9. 启动监控
10. 启动策略主循环
11. 进入交易运行状态

任何一步失败，必须进入安全模式或拒绝启动。

---

# 18. 停止流程

系统停止时必须按顺序做善后：

1. 停止接收新信号
2. 停止新开仓
3. 保留风控与退出能力
4. 停止行情消费
5. 落盘当前状态
6. 清理临时资源
7. 关闭连接
8. 写入停止日志

如果系统是异常停止，重启后必须先做状态恢复。

---

# 19. 状态恢复

重启后必须从持久化数据恢复：

* 当前状态机状态
* 当前持仓
* 当前未成交订单
* 当前冷却状态
* 当前风险快照
* 当前策略版本
* 当前配置版本

恢复原则：

* 不能从内存恢复
* 不能默认当作空仓
* 不能跳过保护单检查
* 不能在状态不明时立即开仓

---

# 20. 故障模式

系统至少要识别以下故障模式：

* 数据源不可用
* 行情延迟
* 数据缺失
* 交易所接口拒绝
* 下单失败
* 保护单失败
* 持仓同步失败
* 数据库写入失败
* 配置加载失败
* 事件总线堵塞
* 风控阈值异常
* 状态机不一致

故障处理原则：

* 能降级则降级
* 不能降级则暂停开仓
* 不能恢复则进入保护模式
* 必须保留日志与审计信息

---

# 21. 保护模式

保护模式下系统行为应收缩为：

* 禁止新开仓
* 允许减仓
* 允许止损退出
* 允许持仓同步
* 允许日志与审计
* 允许人工检查

触发保护模式的条件包括：

* 连续拒单
* 持仓异常
* 风控异常
* 交易所异常
* 数据异常
* 订单状态不一致
* 数据库不可写
* 事件总线不可用

---

# 22. 监控与告警

系统必须具备监控与告警能力。

监控指标至少包括：

* 行情延迟
* 策略循环延迟
* 订单提交延迟
* 成交回报延迟
* 持仓同步失败次数
* 保护单失败次数
* 拒单次数
* 风控阻断次数
* 数据缺失次数
* 系统异常次数

告警对象建议包括：

* Telegram
* Slack
* Email
* 本地日志
* 仪表盘

---

# 23. 可观测性要求

系统应当能够回答：

* 当前是否在交易
* 当前持有什么仓位
* 当前为何不交易
* 当前风险是否安全
* 当前订单状态是什么
* 当前是否处于冷却
* 当前是否处于保护模式
* 当前最近一次异常是什么

如果这些问题不能快速回答，部署架构就不合格。

---

# 24. 容器化建议

如果使用容器化部署，建议至少拆分：

* `strategy-app`
* `backtest-runner`
* `database`
* `monitoring`
* `report-worker`

容器要求：

* 配置文件挂载
* 密钥隔离
* 日志落盘
* 健康检查
* 重启策略明确

---

# 25. 健康检查

健康检查应覆盖：

* 数据库连接
* 交易所连接
* 行情更新
* 事件总线
* 持仓同步
* 风控状态
* 配置状态
* 关键进程存活

建议提供：

* `liveness`
* `readiness`
* `startup` 三类检查

---

# 26. 版本管理

部署必须与版本绑定。

至少记录：

* 代码版本
* 策略版本
* 风控版本
* 配置版本
* 数据版本
* 回测版本
* 报告版本

每次部署都必须写入版本快照。

---

# 27. 发布流程

推荐发布流程如下：

1. 本地单测通过
2. 回测通过
3. Staging 验证通过
4. 配置校验通过
5. 监控接入通过
6. 生产灰度
7. 小规模实盘验证
8. 全量上线

禁止直接从开发环境跳生产。

---

# 28. 回滚流程

任何部署都必须可回滚。

回滚内容包括：

* 代码版本
* 配置版本
* 数据迁移版本
* 策略版本
* 风控版本

回滚原则：

* 回滚后状态机仍可恢复
* 回滚后持仓仍可同步
* 回滚后保护单仍可管理
* 回滚后不能丢失审计记录

---

# 29. 灰度策略

如需逐步上线，建议采用灰度：

* 先单币种
* 再少量币种
* 再扩大标的池
* 再扩大仓位规模

灰度期间必须观察：

* 成交率
* 拒单率
* 保护单成功率
* 风控阻断率
* 状态一致性
* 延迟
* 回撤

---

# 30. 测试要求

部署架构必须接受以下测试：

* 配置加载测试
* 启动测试
* 停止测试
* 重启恢复测试
* 数据库恢复测试
* 保护模式测试
* 告警测试
* 容器重启测试
* 灰度发布测试
* 回滚测试

---

# 31. 禁止项

禁止：

* 开发和生产混用同一配置
* 代码改完直接在线上试
* 没有恢复机制就上线
* 没有保护模式就实盘
* 没有监控就持久运行
* 用内存状态当唯一真相
* 让执行层直接依赖临时脚本
* 让回测任务污染实盘数据库

---

# 32. 推荐部署顺序

建议实施顺序如下：

1. 数据层
2. 指标层
3. 上下文层
4. 信号层
5. 风控层
6. 执行层
7. 回测层
8. 报告层
9. 监控层
10. 实盘上线

---

# 33. 结论

部署架构不是附属文档，而是系统稳定运行的前提。

如果架构不可恢复、不可审计、不可监控，那么策略再好也没有意义。

本系统必须以可恢复性、可观测性、可回滚性为第一优先级。
