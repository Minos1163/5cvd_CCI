## 1. 最重要的红旗：验证通道自己已经给出否定信号

### 1.1 这是本报告中最需要立即关注的矛盾

```
本报告第2节数据：
  HIGH_SCORE_LONG_OFFSET_PROBE 通道 72h 运行结果：
  开仓 3，平仓 3，PnL -0.5684，PF 0（三笔全部亏损）

本报告第5.1节改动：
  顶层 long_threshold_offset 从 10.0 直接改为 0.0

这两件事放在一起看，构成一个直接矛盾：
  为验证"LONG被拦是否冤枉"而专门设计的探针通道，
  刚跑出3笔全负的结果，同一份报告就把限制LONG的门槛直接归零了

这不是"数据支持决策"，是"决策没有等数据"
```

### 1.2 为什么这个矛盾必须被优先处理

```
上一轮（08-04）报告的核心论据是：
  被SIDE阈值拦截的LONG样本（仅2个）blended +0.465R，止损率50%
  基于此建议：先用SCOUT-only的HIGH_SCORE_LONG_OFFSET_PROBE收集20笔样本，
             PF>1.0再考虑正式校准offset

本轮实际发生：
  探针通道只跑出3笔（远低于建议的20笔最小样本量）
  且这3笔的结果是PF=0（与上一轮2个样本的正期望完全相反）
  正确的响应应该是：暂停、增加观察、不要在样本量和方向都不支持时启动全局改动

  但配置已经把offset直接归零，影响的是全局31.6%级别的LONG决策
  （引用08-04报告的量级：SIDE_THRESHOLD_OFFSET_LONG_10.00此前拦截747次/窗口）
```

### 1.3 建议的立即行动

```
在评审通过前，建议：

  选项A（推荐）：暂缓long_threshold_offset归零，恢复为10.0或校准后的中间值
                继续用HIGH_SCORE_LONG_OFFSET_PROBE收集数据至20笔
                若20笔后PF仍<1.0，说明上一轮的2个正样本是噪音，
                当前offset设计基本合理，不需要改动

  选项B（若已上线观察）：明确设定一个短观察窗（如48-72h）+ 硬性熔断
                若LONG侧新增开仓在观察期内PF<0.8，立即回滚至10.0
                不要让"已经改了"成为继续观察的理由

无论选哪个，都不应该在探针通道刚给出3笔全负结果的同一份报告里，
把限制性参数直接归零而不做任何过渡
```

## 2. rank_end 90 扩容：用大炮打蚊子

### 2.1 问题的核心：解决方案的范围远大于问题本身

```
问题：ATOM（排名83）没有被扫描到，错过一段+12.9%的行情
解决方案：把扫描范围从rank 3-25扩大到rank 3-90

这引入的新符号数量：约70个（从13个扩大到约83个候选池）
这些新符号的共同特征：市值更小、流动性更差、波动性更高
（rank 26-90区间的币种，按加密市场惯例，日均波动通常显著高于前25）
```

### 2.2 报告自己已经识别了这个风险，但解决方案不够精确

```
本报告第6.1节已经指出：
  "扩围将引入~70个新币，多数为小市值高波动币"
  "建议评审是否改为'rank 3-40 + ATOM显式加入'的混合方案"

这个自我修正的方向是对的，但仍然值得进一步收紧：

  为什么是rank 3-40而不是继续维持rank 3-25 + 仅ATOM？
  报告没有给出rank 3-40相比rank 3-25能带来什么额外价值的证据——
  唯一被验证过有价值的新符号就是ATOM，其他26-40区间的币种
  同样没有被验证过是否存在类似的错失案例
```

### 2.3 推荐方案：显式白名单，而非范围扩容

```yaml
# 不推荐：扩大整个扫描范围
dry_run_rank_end: 90   # 引入70个未经验证的新符号

# 推荐：维持原有范围，仅显式添加已验证的符号
dry_run_rank_end: 25   # 保持不变
explicit_watchlist_additions:
  - symbol: "ATOMUSDT"
    added_date: "2026-08-07"
    rationale: "08-02牛市段+12.9%漏选案例，见本报告"
    review_period_days: 14
    promotion_criteria:
      min_samples: 10
      pf_min: 1.0

# 未来若有其他类似"错失"案例（如某个rank 30-80区间的币种
# 被证明有明确、可复现的机会），再逐一显式添加，
# 而不是一次性打开整个rank范围
```

### 2.4 为什么"显式添加"比"范围扩容"更符合系统当前的成熟度

```
当前系统状态（综合前几轮报告的诊断）：
  q1_trend_launch刚修复完成，尚未经过完整验收周期
  LONG offset验证通道刚跑出矛盾数据（见第1节）
  SCOUT任务多样化问题尚未解决（多个mission长期0触发）
  RR几何门槛的SHORT侧验证依赖当前13个币种的历史数据

在这些基础问题都还没有稳定验证通过的情况下，
把交易宇宙扩大6倍以上（13→83），意味着：
  所有尚未验证稳定的组件（评分逻辑、门控逻辑、SCOUT路由）
  都要在一个数据特征完全不同、样本更少、噪音更大的新符号池上
  重新证明自己的有效性

这不是渐进式改进，是同时改变"交易什么"和"如何交易"两个维度，
一旦出现问题将难以判断是策略逻辑问题还是新符号池特性问题
```

## 3. N=1 回测的统计意义边界

### 3.1 需要明确说明的统计学事实

```
本报告用来支持整个改动的核心证据是：
  ATOM 08-02 09:45 一笔模拟交易，+1.44R

这是单笔样本（N=1）。任何单笔交易的结果，无论盈亏，
都不能构成"这个方向/这个配置是有效的"的证据。

对比：
  上一轮08-04报告中，SHORT侧RR几何拦截样本有17笔，
  止损率94.1%——这才是具有统计意义的证据基础
  （17笔虽然也不算大样本，但足以观察到一致的模式）

  本轮ATOM的1笔交易，无法排除"运气好"的可能性
```

### 3.2 正确的验证路径：扩大历史回放窗口

```python
# 建议：不要只用08-02~08-05这一段牛市窗口
# 应该用更长的历史窗口，覆盖ATOM在不同市场状态下的表现

def proper_atom_validation_backtest(
    symbol: str = "ATOMUSDT",
    lookback_days: int = 90,   # 至少3个月，覆盖多种市场状态
    config: dict = None
) -> dict:
    """
    用完整的run_live_dry_run闸门链（而非本报告承认的"简化版"）
    回放ATOM在过去90天的表现，而不仅仅是已知有牛市段的4天窗口
    """
    ohlcv = fetch_full_history(symbol, days=lookback_days)
    results = run_full_gate_chain_backtest(ohlcv, config)

    return {
        'total_candidates': results.candidate_count,
        'direct_opens': results.direct_count,
        'probe_opens': results.probe_count,
        'win_rate': results.win_rate,
        'pf': results.profit_factor,
        'sample_size_sufficient': results.probe_count + results.direct_count >= 20,
    }
```

### 3.3 已知的方法论问题：本次回放本身是"简化版"

```
本报告第7节明确承认：
  "回放用系统真实组件...但未跑完整run_live_dry_run闸门链
   (近失/侦察/SCOUT路由简化)，DIRECT/PROBE判定为关键闸门近似"

这意味着：
  即使有更多样本，只要仍然用简化版闸门链回放，
  结果也不能完全代表实盘/dry-run的真实行为

  在做出"添加ATOM"这个决策之前，至少应该用完整闸门链
  重新验证这1笔样本是否依然成立
  （简化版和完整版之间的差异可能恰好决定这笔交易能否真正触发）
```

### 3.4 建议的验证优先级

```
在正式将ATOM加入观察列表之前：

  第一步：用完整闸门链（非简化版）重新回放08-02~08-05窗口，
         确认那1笔PROBE_OPEN在真实链路下依然成立

  第二步：扩大回放窗口至过去60-90天，评估ATOM在非牛市段的表现，
         避免"只在已知有单次好行情的窗口里找证据"的选择性偏差

  第三步：若两步都支持，再考虑显式添加（而非rank扩容）
```

## 6. 数据完整性问题：TONUSDT 与 CCI 口径

### 6.1 TONUSDT 零行数据需要排查

```
表格显示：TONUSDT rows=0（整个窗口没有任何决策记录）

这与其他13个符号形成鲜明对比（其余符号至少有16-256行）
可能的原因：
  a) TON数据源本身存在缺失或API异常
  b) TON方向判断长期返回NONE（如报告推测）
  c) TON被某个更早期的符号策略静默排除（需要检查配置）

在没有排查清楚之前，不应该假设这只是"待查"的次要问题——
如果原因是(a)，说明当前数据管道存在其他符号也可能受影响的隐患；
如果原因是(c)，说明可能存在另一个未被文档化的排除规则，
类似本次ATOM排名过滤的问题可能在其他符号上重演
```

### 6.2 CCI 口径差异的处理原则

```
报告诚实披露了这个差异：
  用户观察的CCI顶/跌穿时点与系统20周期CCI计算结果不一致
  报告判断"不影响'这是明确多头段'的整体判断"

这个处理是合理的，但建议补充一点：
  既然CCI是当前六组件评分体系中的独立一环（cci_momentum_quality，14分权重），
  如果用户日常观察使用的CCI周期/参数与系统内部不同，
  可能意味着人工复核这类"错失案例"时容易产生系统性偏差——
  人工观察到的"CCI已经进入健康区间"的时点，
  系统内部实际判断可能仍处于极值区（如本例08-04 00:00 CCI差异94.9 vs 用户描述的不同）

建议：在人工提出"某标的行情很好为什么没开仓"类的排查请求时，
     统一先用系统内部实际参数（CCI period=20等）复现，
     避免因为参数口径不同而误判系统存在缺陷
```

### 7.2 显式白名单机制的完整规格

```python
@dataclass
class ExplicitWatchlistEntry:
    symbol: str
    added_date: str
    rationale: str            # 添加理由（如具体的错失案例描述）
    scan_scope: str           # "scout_only" | "full_pipeline"
    review_period_days: int = 14
    promotion_criteria: dict = None

def evaluate_watchlist_candidate_for_addition(
    symbol: str, historical_backtest_result: dict
) -> ExplicitWatchlistEntry | None:
    """
    未来任何"某标的被错过"的案例，走此流程而非直接改rank范围
    """
    if historical_backtest_result['sample_size'] < 20:
        return None   # 样本不足，先用完整闸门链扩大回放窗口

    if historical_backtest_result['pf'] < 1.0:
        return None   # 扩大样本后若不再支持，不添加

    return ExplicitWatchlistEntry(
        symbol=symbol,
        added_date=today(),
        rationale=historical_backtest_result['case_description'],
        scan_scope="scout_only",   # 首次添加一律先进SCOUT，不直接主账本
        promotion_criteria={"min_samples": 15, "pf_min": 1.0}
    )
```

## 8. 验证协议

### 8.1 长offset恢复后的观察指标

```
恢复long_threshold_offset至10.0（或中间校准值）后：
  继续运行HIGH_SCORE_LONG_OFFSET_PROBE
  目标：累计20笔样本

  20笔后决策树：
    PF > 1.0 且 blended_R > 0.3 → 可以考虑正式校准offset（而非直接归零）
    PF < 0.8 → 维持offset=10.0，本次改动的假设不成立
    介于两者之间 → 继续观察至30笔
```

### 8.2 ATOM 完整闸门链复验

```
在批准targeted_long_symbols添加ATOM之前：
  用完整run_live_dry_run闸门链（非本报告的简化版）
  重新跑08-02~08-05窗口，确认1笔PROBE_OPEN依然成立

  同时扩大回放至过去60-90天：
    若ATOM在此期间产生>=10笔候选且整体PF>1.0 → 支持添加
    若样本过少或PF不佳 → 本次的+1.44R很可能只是单次幸运
```

### 8.3 TONUSDT 数据排查

```
优先级：与上述并行处理，不阻塞其他决策
排查步骤：
  1. 检查TON的原始K线数据是否在08-02~08-05期间完整
  2. 检查symbol universe构建逻辑，确认TON未被某个隐藏规则排除
  3. 若数据源正常且未被排除，检查方向判断逻辑为何长期返回NONE
```
