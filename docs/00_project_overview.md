# Project Overview

Version: V1.0

---

# 1. 项目名称

多周期主流虚拟币趋势交易系统

英文名建议：

`crypto-mtf-trend-strategy`

---

# 2. 项目目标

本项目的目标是构建一套可回测、可实盘、可审计、可维护的 Binance USDT 永续合约交易系统，用于交易市值前 20 的主流虚拟币。

系统只做一件事：

在可控风险下，基于多周期结构识别趋势，捕捉中短线交易机会，并以统一的状态机、仓位模型和风控模型执行。

---

# 3. 重构背景

旧系统已经演化成不可维护的复杂结构，主要问题包括：

- 信号层过度复杂
- 多层 gate 互相叠加
- watchlist / promotion 套路断裂
- 仓位 floor / cap 逻辑冲突
- 止损逻辑多头并行
- 实盘行为不可预测
- 回测和实盘难以同构

因此，本项目不是在旧系统上补丁式修改，而是一次彻底重构。

---

# 4. 核心设计目标

本项目的核心设计目标如下：

1. 逻辑清晰。
2. 多周期职责明确。
3. 指标职责单一。
4. 状态机可追踪。
5. 仓位契约稳定。
6. 风控规则统一。
7. 回测与实盘同构。
8. 执行层薄而稳定。
9. 数据契约固定。
10. 所有行为可回放、可审计。

---

# 5. 交易标的范围

默认交易对象为 Binance Futures USDT Perpetual 合约中的主流币种。

标的范围：

- 市值前 20 主流虚拟币
- 具备足够流动性
- 非明显下架风险资产
- 非低流动性边缘资产

标的池应支持动态更新，但更新规则必须稳定、可审计、可回测。

---

# 6. 核心交易周期

系统只使用以下周期：

- 15m：执行周期
- 30m：确认周期
- 1H：方向周期
- 4H：背景参考周期

周期职责必须明确：

- 15m 决定“现在能不能进”
- 30m 决定“趋势质量是否足够”
- 1H 决定“方向是否成立”
- 4H 只负责“市场背景参考”，不参与强制裁决

---

# 7. 指标体系

本项目只使用以下核心指标：

- MACD
- CCI
- BOLL
- RSI
- CVD
- ATR

指标职责划分如下：

- MACD：趋势与动量
- CCI：强弱与偏离
- BOLL：波动结构与扩张收缩
- RSI：回调质量与过热状态
- CVD：资金流与主动买卖力量
- ATR：止损、止盈、仓位与波动率风控

原则：

- 一个指标只能服务一类职责
- 不允许指标职责重叠
- 不允许指标既当方向又当风控又当入场触发

---

# 8. 策略哲学

本系统采用的是结构化趋势交易思想，而不是复杂打分器。

策略哲学：

1. 高周期定方向。
2. 中周期定质量。
3. 低周期定时机。
4. 资金流做确认。
5. 波动率做约束。
6. 风险先于收益。
7. 宁可不做，也不要乱做。

---

# 9. 交易决策原则

所有交易决策都必须满足以下原则：

- 多周期同向优先
- 结构完整优先
- 资金流同向优先
- 波动率合理优先
- 数据质量合格优先
- 风控通过优先
- 可执行仓位优先

禁止：

- 弱信号直接重仓
- 复杂 promotion 补仓逻辑
- 信号层和执行层各自解释仓位
- 让低周期噪声推翻高周期背景
- 让临时补丁成为主策略

---

# 10. 开仓形式

系统只允许两种开仓形式：

## 10.1 Probe
试探仓。

特征：

- 仓位更小
- 用于验证方向是否延续
- 适用于高周期方向成立但低周期确认不完整的场景

默认比例：

- 25% 标准仓

## 10.2 Direct
正式开仓。

特征：

- 仓位为标准仓
- 适用于多周期完整确认的场景
- 可进入正常持仓管理流程

默认比例：

- 100% 标准仓

---

# 11. 不做的事情

本项目明确不做以下事情：

- 不做高频
- 不做套利
- 不做做市
- 不做黑盒机器学习预测
- 不做复杂多层 watchlist/promotion 链路
- 不做信号层、风控层、执行层相互补丁式修正
- 不做“为了开仓而开仓”的策略

---

# 12. 风控目标

风控目标优先级高于收益目标。

风控目标包括：

- 控制单笔亏损
- 控制单币风险
- 控制组合总暴露
- 控制日内亏损
- 控制周内亏损
- 控制回撤
- 控制波动异常时的暴露
- 控制连续亏损后的重试冲动

---

# 13. 仓位目标

仓位系统必须满足：

- probe 和 direct 语义稳定
- 仓位与止损距离联动
- 仓位与波动率联动
- 仓位与账户权益联动
- 仓位与组合暴露联动
- 仓位与最小名义额联动

禁止：

- 逻辑小仓，实际大仓
- 仓位被 floor/cap 逻辑扭曲
- 实盘和回测仓位逻辑不一致
- 执行层重新解释仓位意图

---

# 14. 回测目标

回测的目标不是“曲线好看”，而是验证策略是否真实可执行。

回测必须满足：

- 与实盘同构
- 不使用未来数据
- 记录逐笔交易
- 记录状态机
- 记录失败样本
- 记录风控阻断
- 记录仓位计算过程
- 可重复运行
- 可比较版本差异

---

# 15. 实盘目标

实盘的目标不是频繁交易，而是稳定地执行经过验证的交易逻辑。

实盘必须满足：

- 策略状态可恢复
- 订单状态可追踪
- 持仓状态可同步
- 保护单可修复
- 风控可阻断
- 异常可告警
- 所有行为可审计

---

# 16. 系统边界

系统分为以下核心层：

- 数据层
- 指标层
- 上下文层
- 信号层
- 状态机层
- 风控层
- 仓位层
- 执行层
- 回测层
- 报告层
- 监控层

每一层职责必须清晰，禁止跨层越权。

---

# 17. 关键模块关系

模块依赖方向必须保持单向：

```text
Data Layer
  -> Indicator Layer
  -> Context Layer
  -> Signal Engine
  -> State Machine
  -> Risk Engine
  -> Position Sizing
  -> Execution Engine
  -> Backtest Engine
  -> Reporting / Monitoring
```

原则：

* 上层可以调用下层
* 下层不能反向依赖上层
* 执行层不能反向决定策略
* 风控层不能反向决定市场方向

---

# 18. 必须统一的契约

本项目必须统一以下契约：

* 数据契约
* 指标契约

* 状态机契约

---

# 19. 项目成功标准

以下目标是本项目的成功标准：

* 能稳定生成交易信号
* 能稳定执行开平仓
* 能稳定记录状态和日志
* 能稳定回测并复现实盘逻辑
* 能稳定管理 probe / direct 仓位
* 能稳定控制回撤
* 能稳定维护多周期一致性
* 能稳定恢复持仓与订单状态

# 20. 代码实现原则

Codex 编码时必须遵守以下原则：

1. 先定义契约，再写实现。
2. 先写数据结构，再写逻辑。
3. 先写回测，再写实盘。
4. 先写单测，再写集成。
5. 先保证同构，再考虑优化。
6. 先保证可解释，再考虑性能。
7. 先保证能复现，再考虑扩展。
8. 先保证稳定，再考虑花哨。

后续所有文档、代码、测试、回测、执行与部署，都必须围绕本文件中的原则展开。
