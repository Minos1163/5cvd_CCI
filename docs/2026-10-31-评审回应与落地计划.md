## 0. 先核对，再计划

评审的 P0 第 1 条是"逐笔核对 `net_pnl` 是否含建仓成本"。我先做了这件事，同时核对评审自己引用的两个数字。结论：**评审的方向判断基本正确，但它引用我的两个数本身是我算错的**。

### 0.1 我的稿件有三处硬错误（评审发现症状，原因不是它说的那个）

| 稿件数字 | 我的算法 | 真实值 | 根因 |
|---|---:|---:|---|
| 决策总数 20,475 | 把 6 个日切片的 `summary.json:decision_counts` 相加 | **5,850** | 该字段是**运行以来累计计数器**，不是当日增量；相加 = 重复计 6 次 |
| gate 分层 side_policy 6,261 等 | 同上 | **1,719** | 同上 |
| 近似单覆盖 190/602 = 31.6% | 同上 | **190/190 = 100%** | `near_misses.jsonl` 按日轮转，6 文件合计恰好 190；末日 `near_miss_count` 也是 190 |

**证据**（可直接复核）：

```
2026-10-26/decisions.jsonl  rows=429   span 10-26 15:45 → 23:45  bars=33
2026-10-27/decisions.jsonl  rows=1248  span 10-27 00:00 → 23:45  bars=96
…
2026-10-31/decisions.jsonl  rows=429   span 10-31 00:00 → 08:00  bars=33
unique (symbol, bar) = 429 + 1248×4 + 429 = 5,850 = 13 标的 × 450 根
```

`decisions.jsonl` **每 (symbol, bar) 恰好一行，无重复**。评审 D10 推断的"每根 bar 多行决策、漏斗被重复行污染"**不成立**；但"行数对不上、先核对再算"的结论**成立**，因为我把累计值当增量相加了。

这意味着：评审 Q5（190/602 是否足以支撑第四节）的**前提消失**——覆盖率是 100%，不是 31.6%。反事实的样本代表性仍需单独讨论（近似单是高分条件子集），但不再是"只看了三分之一"的问题。

### 0.2 评审指出的口径问题成立，且比它说的更彻底

`paper_trading.py:371-395` 的 `net = gross - exit_fee - exit_slip` **不含建仓成本**；建仓成本在 `open_position` 里以 `position.realized_pnl = -(entry_fee + entry_slip)` 记入，但没有写进任何 `PAPER_CLOSE` 事件的 `net_pnl`。

所以我稿件里的分维度表（象限/方向/通道/出场原因）用的是 **close-only**，头条 `equity` 用的是 **full-cost**。两者差 5.90（主账本）/ 0.23（AB 账本 3 个未平仓位），与评审的对账推导完全一致：

```
9.42 − 5.87 = 3.55    ← close-only 合计（通道表 / 象限表之和）
9.42 − 11.77 = −2.35  ← full-cost（头条）
3.55 − 36.49 = −32.94 ← 稿件"剔除 2 笔后 9 笔"（close-only）
−2.35 − 36.49 = −38.84 ← 同口径下应为这个
```

## 2. 任务清单

### T1 口径对账（P0，主控执行）

**做**：`paper_trading.py` 的 `_close_fraction` 增加 `gross_pnl`（已有）、`entry_cost`、`exit_cost`、`net_pnl_full`、`pnl_schema_version=2` 五个字段；建仓成本按 `fraction` 比例摊到每次减仓。

**验收**：`experiment_*_loss_limit` 的触发阈值在修复前后相差 3–4 倍（用 10B 数据回放验证）；`realized_margin_pnl` 旧值不被覆盖。

**验收**：每格 ≥3,000 样本；报告毛 `E[R]` 与 `cost_R` 分列；给出"毛差异是否显著"的结论；**先写下先验预测**（见 §4）。

**验收**：给出 accepted 与 rejected 在同一引擎下的 E[R]、差值的块级 bootstrap 95% CI。
