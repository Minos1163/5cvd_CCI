## 2. P0-1：mirror A/B 停用决策的完整评估

### 2.1 证据强度：三轮独立窗口一致

```
窗口          样本量    PF(legacy)   PF(trend)    判定
──────────────────────────────────────────────────────
08-04窗口      未知     0.345        0.370        负期望
08-11窗口      66笔     0.0426       0.0109       负期望（恶化）
08-18窗口      98笔     -9.99（合计）              负期望（持续）

三个独立时间窗口、不同市场状态下，mirror账本持续负期望，
且样本量已经足够大（98笔），这是本项目迄今为止证据链
最完整、最一致的一个负期望判定
```

### 2.2 完全同意停用/降级，且建议明确选择"降级为shadow"而非直接关闭

```
理由：mirror账本的价值不仅在于"是否盈利"，还在于
     "验证放行候选是否有效"这个持续的假设检验功能

  若完全关闭mirror，未来任何"是否应该放宽某个门槛"的讨论，
  会失去一个可以快速验证的观测通道

  改为shadow-only（记录但不实际计入亏损/风险敞口），
  既能停止实质性亏损，又能保留这个诊断价值
```

### 2.3 具体的降级规格

```python
@dataclass
class MirrorABShadowConfig:
    mode: str = "shadow_only"          # 从 active_paper 改为 shadow_only
    notional_multiplier: float = 0.0    # 不再计入实际敞口
    logging_enabled: bool = True        # 继续完整记录假设路径的盈亏
    reactivation_criteria: dict = None

reactivation_criteria = {
    "min_consecutive_positive_batches": 3,   # 连续3个batch转正才考虑重新激活
    "min_batch_size": 20,
    "note": "重新激活前，先审查是哪类候选（按08-11 Task D的分桶方式）"
           "在shadow期间转正，只重新激活那个特定分桶，而非整体mirror"
}
```

### 2.4 mirror停用不应影响对08-11 Task D分桶报告的推进

```
mirror账本停用（或降级为shadow）之后，08-11报告设计的
"按source_reason/quadrant/side/symbol分桶评估"（Task D）
依然应该继续执行——只是评估对象从"是否应该正式开仓"
变成"shadow数据中哪些分桶显示出转正迹象"

这样mirror的历史价值（三轮一致的负期望证据）和未来价值
（继续作为低成本假设检验工具）都被保留，只是不再承担
实际资金层面的持续亏损
```

## 3. P0-2：q1_trend_launch "特征提炼"需要先纠正一个方法论风险

### 3.1 需要明确指出的统计学问题

```
本报告建议："提炼该样本(SOL SHORT +6.25)的入场特征...
            形成'可盈利子集'假设"

这里的样本量是N=2（SOL +6.25，BNB -0.155）。
从2个样本中"提炼特征"来区分"可盈利子集"和"不可盈利子集"，
在统计学上几乎没有意义——任何两个样本之间的差异，
都可以构造出一个"看似合理"的区分特征，但这极大概率是过拟合

这与本项目此前多次强调的原则完全一致：
  08-02报告：反对基于5个ZEC样本直接解除黑名单
  08-04报告：反对基于2个LONG offset样本直接改全局参数
  本轮如果基于2个q1_trend_launch样本"提炼特征"，是同一类错误的重现
```

### 3.2 正确的处理方式

```
现阶段（N=2）能够合理做的事：
  ✅ 记录这2个样本的完整特征（象限/组件分数/extreme_ratio/
     出场路径），作为未来样本积累后的对照数据
  ✅ 确认"至少存在一个盈利样本"这个事实本身
     （证明通道不是结构性无法盈利，这是有价值的阶段性结论）
  ✅ 继续观察，不做任何参数调整或"聚焦盈利子集"的路由改动

现阶段不应该做的事：
  ❌ 基于2个样本构造任何形式的"筛选规则"
     （例如"以后只开类似SOL SHORT模式的信号"）
  ❌ 提高该通道的仓位或杠杆（notional_multiplier保持62.5不变）
  ❌ 在报告中使用"证明可盈利子集存在"这类过强的表述
     （本轮报告"通道可盈利的实证"这个表述本身是准确的——
      通道确实产生过盈利样本——但不应该被理解为
      "已经找到了盈利子集的判定规则"）
```

### 3.3 建议的样本积累目标

```
q1_trend_launch通道建议积累至少15-20笔样本后，
再进行"特征提炼"级别的分析。在此之前的每一轮报告，
只需要如实记录新增样本的specific outcome，
不需要（也不应该）尝试从中总结规律
```

## 5. 统一的小样本决策框架

### 5.1 本轮报告实际上暴露了一个需要被明确写下来的通用规则

```
纵观整个项目的历史（从08-02到本轮），反复出现同一种张力：
  新通道刚开始产生样本时，无论正负，都容易被过度解读
    - 正样本 → 想要"提炼特征"、"扩大规模"
    - 负样本 → 想要"立即关闭"、"回滚参数"

  但从ZEC的5个样本、LONG offset的2-3个样本，
  到本轮q1_trend_launch的2个样本、Q3→Q1的3个样本，
  这个模式反复出现，说明需要一个通用的、可直接引用的规则，
  而不是每次都重新讨论"这个样本量是否够用"
```

### 5.2 建议固化的规则

```python
SAMPLE_SIZE_DECISION_RULES = {
    "min_samples_for_any_narrative": 10,
    # 少于10个样本，报告中不应该出现"提炼特征"、"证明有效"、
    # "可盈利子集"这类具有解释性/因果性含义的表述，
    # 只能陈述客观发生的结果（"这N笔的结果是..."）

    "min_samples_for_parameter_adjustment": 20,
    # 少于20个样本，不进行任何门槛/权重/仓位的调整
    # （这是08-04、08-11报告已经反复使用的标准，本轮固化为通用规则）

    "min_samples_for_priority_boost": 20,
    # 少于20个样本，不应该给予该通道更高的mission路由优先级
    # 或更多的资源倾斜，即使当前表现是正的

    "negative_signal_special_case": {
        "consecutive_windows_required": 2,
        "rationale": "若同一通道在2个独立时间窗口都显示强烈负期望"
                     "（如mirror的三轮一致），即使单窗口样本量不算很大，"
                     "也可以采取停用/降级行动——因为跨窗口一致性"
                     "本身就是一种更强的证据形式，弥补了单窗口样本不足"
    }
}
```

### 5.3 这个框架如何应用于本轮的四个决策

```
mirror A/B：满足negative_signal_special_case（三轮一致）→ 可以停用/降级
q1_trend_launch：2笔，未达min_samples_for_any_narrative → 只记录，不提炼
Q3_TO_Q1_CONFIRMATION：3笔，同上 → 只记录，不提炼，不优先
Q2_PENDING_MOMENTUM：3笔，同上 → 只记录
HIGH_SCORE_LONG_OFFSET_PROBE：5笔，同上，且已有08-11决策树 → 遵循既定决策树
```


### 6.2 建议为所有小样本通道统一使用累计追踪器

```python
@dataclass
class ChannelCumulativeTracker:
    channel_name: str
    cumulative_samples: int
    cumulative_pnl: float
    first_sample_date: str
    last_sample_date: str
    windows_observed: int          # 跨越了几个报告窗口
    decision_threshold: int = 20
    samples_remaining_to_threshold: int = None

    def __post_init__(self):
        self.samples_remaining_to_threshold = max(
            0, self.decision_threshold - self.cumulative_samples
        )

# 建议：这个追踪器应该作为一个持久化的状态文件
# （例如 state/channel_cumulative_tracking.json），
# 每轮报告更新后直接读取展示，而不是每次重新从日志计算
# 一个可能因为"窗口切分方式不同"而产生歧义的数字
```

## 9. 一句话结论

```
这是一份标志着阶段转换的报告：管道死锁问题在经历四轮诊断
和一次流程升级后，终于得到真正解决，这本身值得被记录为

（mirror停用已经证据充分，可以直接执行），
而是把"20笔样本门槛"这个此前已经零散使用过的标准，
正式固化为所有小样本通道的统一纪律——
避免在管道问题解决之后，又在样本解读环节重蹈类似的过早下结论的覆辙。
```

### A.2 这条时间线的方法论价值

```
这个案例完整展示了一个诊断驱动的工程改进流程从
"持续发现问题但未落地"到"升级处理方式后真正解决"的全过程，
其中几个关键节点值得被总结为可复用的经验：

  经验一：当同一类问题连续两轮以上被诊断出但未验证落地时，
         应该升级处理方式（从"继续诊断"改为"直接代码审查"），
         而不是产出第三、第四份类似的诊断报告

  经验二：探针/验证通道给出的信号（即使只有2-3个样本）
         应该被认真对待，不应该在同一份报告中被忽略后
         直接执行相反的全局参数改动（08-07的教训）

  经验三：直接代码审查往往能发现日志行为反推无法定位的问题
         （data_health粘滞降级就是在代码审查中被额外发现的）

这条时间线本身应该被保留为项目内部的参考案例，
未来遇到类似"配置改了但效果一直不出现"的情况时，
可以直接参照这个升级路径，而不需要重新摸索处理方式
```
