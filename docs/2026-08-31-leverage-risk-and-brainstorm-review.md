## 4. 我的补充头脑风暴一：单笔风险预算硬约束

### 4.1 这是本报告"风控缺口"部分已经点出但未给出完整规格的内容

```
报告第4.2节已经诊断："缺少'单笔最大风险'的硬约束"
本节给出具体的实现规格
```

### 4.2 核心设计：按风险（而非按敞口）计算仓位

```python
def compute_position_size_by_risk_budget(
    equity: float,
    entry_price: float,
    stop_price: float,
    leverage: int,
    max_risk_pct_of_equity: float = 0.012,   # 单笔最大风险=账户权益的1.2%
) -> float:
    """
    核心区别：当前 notional_hint 是按"敞口百分比"计算
    （exposure_pct × equity），本函数按"风险百分比"计算——
    即使止损被触发，最大损失也被锁定在 equity × max_risk_pct

    这与当前的max_total_exposure_pct（总敞口上限）不冲突，
    是在敞口上限之下再加一层更精细的单笔风险上限
    """
    stop_distance_pct = abs(entry_price - stop_price) / entry_price

    if stop_distance_pct <= 0:
        return 0.0  # 异常保护

    max_notional_by_risk = (equity * max_risk_pct_of_equity) / stop_distance_pct

    return max_notional_by_risk


def apply_risk_budget_cap(
    original_notional_hint: float,
    equity: float,
    entry_price: float,
    stop_price: float,
    leverage: int,
    config: dict,
) -> tuple[float, str]:
    """
    在现有_notional_hint计算完成后，追加这一层风险预算裁剪
    """
    risk_capped_notional = compute_position_size_by_risk_budget(
        equity, entry_price, stop_price, leverage,
        config.get('max_risk_pct_of_equity', 0.012)
    )

    final_notional = min(original_notional_hint, risk_capped_notional)

    capped = final_notional < original_notional_hint
    reason = "RISK_BUDGET_CAPPED" if capped else "RISK_BUDGET_NOT_BINDING"

    return final_notional, reason
```

### 4.3 用本轮三笔大额亏损验证这个设计的效果

```
反事实计算（基于报告已披露的数据）：

  假设三笔亏损的stop_distance_pct约为止损公式给出的
  ATR×1.5（clamp 0.5%-3%），margin_used≈486，leverage=4
  → 原始notional ≈ 486 × 4 = 1944

  若max_risk_pct_of_equity=1.2%，假设账户equity约10000
  （延续项目此前报告的初始equity量级）：
    max_risk_budget = 10000 × 0.012 = 120

    若stop_distance_pct=1.5%（典型ATR×1.5值）：
    risk_capped_notional = 120 / 0.015 = 8000（未触及风险上限，
    因为1944远小于8000——说明问题不在notional过大本身）

  这个反事实计算提示一个重要的诊断方向：
  若risk_capped_notional计算结果显示"当前仓位其实远低于
  风险预算上限"，说明这三笔亏损的根因不是"仓位太大"，
  而纯粹是"止损距离设置或入场位置判断"的问题——
  仓位大小本身可能不是这次亏损的直接原因，
  只是放大了一个本来就存在的入场质量问题

  建议：在实施risk_budget硬约束之前，先用这三笔的
  真实entry/stop价格重新计算，确认risk_capped_notional
  是否真的会裁剪这三笔的仓位。如果计算显示不会裁剪
  （如上面的示意计算所示），说明这个硬约束虽然仍然值得
  作为长期护栏加入，但不能被误认为"加了这个就能避免
  这三笔亏损"——需要同时配合候选1的行为确认门槛
```

## 5. 我的补充头脑风暴二：杠杆应由质量分数驱动，而非静态tier

### 5.1 观察到的问题

```
报告第4.1节数据："主账本杠杆：4（实测大仓）...
aggressive tier下常规仓杠杆；leverage_5x_*门槛存在但实测为4"

这句话暗示了一个结构：5x杠杆有严格的质量门槛
（fib≥13, pa≥9, rr≥4），但leverage=4似乎是一个
"默认的aggressive tier"，没有同等严格的质量要求——
换句话说，从4x到5x有严格把关，但从"不给杠杆/降级PROBE"
到"给4x"之间的把关力度未知
```

### 5.2 建议的设计：三档杠杆全部质量门控，而非只有顶档

```python
LEVERAGE_TIER_QUALITY_GATES = {
    5: {
        "fib_min": 13.0, "pa_min": 9.0, "rr_min": 4.0,
        "cci_min": 7.0,  # 延续此前报告的5x设计
        "breakout_confirmation_required": True,  # 新增：候选1的应用
    },
    4: {
        # 当前可能缺失的层级——建议补充与5x同等严格程度的门槛，
        # 只是数值上略宽松，而非"只要总分够就默认4x"
        "fib_min": 10.0,
        "pa_min": 7.0,
        "rr_min": 5.0,   # 注意：这里故意设置RR要求不低于5x的4.0，
                          # 因为本轮三笔大额亏损的MFE都未达1R，
                          # RR几何质量可能恰恰是4x档位被忽视的缺口
        "breakout_confirmation_required": False,  # 可选：观察期先记录不强制
    },
    3: {
        "fib_min": 6.0,
        "pa_min": 6.0,
        "rr_min": 2.0,
    },
    2: {
        # 默认/保守档，DIRECT基础门槛之上不设额外要求
    }
}

def select_leverage_with_quality_gate(
    total_score: float, component_scores: dict, config: dict
) -> tuple[int, str]:
    """
    从最高档位开始尝试，逐级降级直到满足条件
    """
    for tier in [5, 4, 3, 2]:
        gates = LEVERAGE_TIER_QUALITY_GATES.get(tier, {})
        if all(
            component_scores.get(k.replace('_min', ''), 0) >= v
            for k, v in gates.items()
            if k.endswith('_min')
        ):
            return tier, f"LEVERAGE_{tier}X_QUALITY_GATE_PASSED"

    return 1, "LEVERAGE_DEFAULT_MINIMUM"  # 均不满足时的保底
```

### 5.3 这个设计如何与候选2（波动率自适应）协同

```
两者不冲突，是两个独立维度的裁剪：
  维度一（本节）：杠杆上限由信号质量（RR/PA/Fib/CCI）决定
  维度二（候选2）：杠杆上限由市场波动率（ATR分位）决定

  最终杠杆 = min(质量驱动的杠杆上限, 波动率驱动的杠杆上限)

建议实施顺序：先做维度一（质量驱动），因为：
  a) 复用了已有的组件评分（不需要新增ATR分位计算）
  b) 直接针对本轮报告发现的"MFE<1R"问题——
     RR几何分数低的信号本就不该给到4x
  c) 候选2需要额外的历史ATR分位统计基础设施，实施周期更长
```

## 7. 样本量纪律：3笔不足以下强结论，但足以立即加硬约束

### 7.1 需要明确区分两类行动

```

     "是否应该有风险预算上限"这个问题本身）

```
